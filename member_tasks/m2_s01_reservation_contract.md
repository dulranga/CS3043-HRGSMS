## Target reservation invariants

- `booking` is one guest/reference/channel header with at least one `booking_room_line`. Each line owns its stay dates, guest count, LKR rate snapshot and status. The target has no writable booking-header dates/count/rate/status/actual times; booking-wide summaries are derived. The existing header columns are legacy implementation to retire in M2-S27.
- `booking_room_assignment` links one room line to one physical room and keeps closed assignment rows. A BOOKED or CHECKED_IN line has exactly one open assignment; a terminal line has none. A booking may have several open assignments, one per active line. The existing `room.booking_id` pointer is removed in M2-S22 and never used for availability/occupancy.
- Line stay intervals are `[stay_start_date, stay_end_date)` in hotel dates. Active BOOKED/CHECKED_IN lines cannot overlap on one physical room; adjacent stays can. All lines of one booking must be in one branch. Availability and new assignment writes check blocks, room/branch/room-type active states and capacity. PostgreSQL must reject conflicting concurrent writes independently of Express search results.
- `room_type.base_daily_rate` and `booking_room_line.rate_snapshot` use exact LKR `numeric(12,2)`. The server snapshots the displayed pre-discount/tax base rate at confirmation; absent an approved override, simultaneous rooms of one type share that type's rate, while different types may differ. A changed catalogue quote before confirmation must be shown and reconfirmed. Each line's fixed nightly snapshot survives later catalogue changes; pre-check-in edits preserve previous values in revisions and refresh the DRAFT bill. After check-in the line dates/rate stay fixed, including on a room move; approved differences use explicit invoice adjustments, never retroactive repricing. Physical moves are preserved by assignment occupancy instants. See SRS §4.7.4 for the billing policy.
- Line statuses use BOOKED, CHECKED_IN, CHECKED_OUT, CANCELLED and NO_SHOW with independent per-line check-in/checkout/cancellation/no-show. Booking-wide progress is a read-only summary that must show mixed/partial states honestly. Actual occupied room periods belong to assignments, not their `assigned_at`/`unassigned_at` transaction-time fields.
- `enum(4)`, `enum(11)` and `enum(14)` are source-ER annotations, not PostgreSQL lengths or a required count of labels. The target Member 2 value sets, including the amended physical room conditions, are recorded below.

For M2-S02, catalogue names are required, non-blank `varchar(255)` values; `amenity.description` may be null. Neither catalogue name receives an unapproved uniqueness constraint. `capacity` is positive `smallint`; the rate is non-negative and finite. Both PKs are UUIDv7, and the link table has only its two UUID FKs as composite PK. Link FKs use restricted parent deletion; catalogue records with references are deactivated instead of deleted. These constraints preserve Table 40's attributes without introducing new columns.

The room-type and amenity catalogues have no branch FK, so their values are chain-wide. Under the SRS working role matrix, only CHAIN_MANAGER may edit them, including `room_type.base_daily_rate`; BRANCH_MANAGER may edit physical rooms and dated blocks only in the assigned branch. Member 1 and API owners review/test that role matrix under TBD-15 before dependent write APIs.

M2-S28 guards later capacity/type edits: lowering a room type's capacity must not put any current BOOKED/CHECKED_IN assigned line above capacity, and a room with any such line cannot change type at all because the guest reserved that category. Reject conflicting edits under the same booking/catalogue lock contract; historical lines and agreed rate snapshots stay unchanged.

For the target room schema, room numbers are required non-blank `varchar(255)` values and unique within a branch. Every room requires a branch and room type, defaults to active/READY, and has no `booking_id` column. A room block requires a non-blank reason, creator and half-open `[start_date,end_date)` interval with `end_date > start_date`. Dated blocks represent limited outages; physical OUT_OF_SERVICE represents extended outages. New/edited blocks conflict with current overlapping BOOKED/CHECKED_IN assignments, while room/branch/type deactivation or room OUT_OF_SERVICE conflicts with any affected current BOOKED/CHECKED_IN assignment; reassign/cancel before retrying, never delete history. Legacy RESERVED may reflect a provable booking assignment or an explicit dated manual block; do not invent a block for the assignment case. Parent deletion is restricted. M2-S04 historically implemented the prior pointer/five-label schema; M2-S22/S23 must migrate it safely, and M2-S06 enforces assignment/block/active-parent integrity.

Branch deactivation is stricter than an ordinary room move: same-booking cross-branch moves are prohibited, so all affected assignments must close through valid cancellation or completed stays before deactivation.

M2-S05 historically created UUIDv7 assignments with booking/room FKs, ordered `assigned_at`/`unassigned_at` instants and a partial unique index on `booking_id WHERE unassigned_at IS NULL`. That migration and its tests describe the former single-room contract, not the target. M2-S26 rekeys each assignment to a `booking_room_line`, adds actual `occupied_from`/`occupied_to` instants and replaces the index with one open assignment per line. There is deliberately no simple open-row uniqueness on `room_id`, because different future bookings may use a room on non-overlapping dates; M2-S06 enforces same-room interval conflicts and checked-in occupancy. `assigned_at` is when the assignment decision was made, not the hotel-night period or actual occupancy.

The operation owner writes exactly one `booking_room_line_status_history` row per line transition through Member 2's interface in the same transaction. Old `booking_status_history` rows remain legacy evidence but do not mirror every new line event. Member 3 owns `room_status_history`, written only for real physical-condition changes. Member 1 owns `audit_log`. The database must reject inconsistent direct line/assignment/status writes, including two CHECKED_IN lines on one room or two overlapping active lines for the same room. Members 2–4 must agree on one lock order, PostgreSQL overlap/consistency guard and safe retry behavior before implementation. Exceptional correction requires a separately audited policy.
