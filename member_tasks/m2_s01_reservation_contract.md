## Target reservation invariants

- `booking` is one guest/reference/channel header with at least one `booking_room_line`. Each line owns its stay dates, guest count, LKR rate snapshot and status. The schema has no writable booking-header dates/count/rate/status/actual times; booking-wide summaries are derived.
- `booking_room_assignment` links one room line to one physical room and keeps closed assignment rows. A BOOKED or CHECKED_IN line has exactly one open assignment; a terminal line has none. A booking may have several open assignments, one per active line. `room.booking_id` is never created or used for availability/occupancy. M2-S05 enforces the one-open-row-per-line base rule; M2-S06 enforces the transaction-end lifecycle and occupancy rules.
- Line stay intervals are `[stay_start_date, stay_end_date)` in hotel dates. Active BOOKED/CHECKED_IN lines cannot overlap on one physical room; adjacent stays can. All lines of one booking must be in one branch. Availability and new assignment writes check blocks, room/branch/room-type active states and capacity. PostgreSQL must reject conflicting concurrent writes independently of Express search results.
- `room_type.base_daily_rate` and `booking_room_line.rate_snapshot` use exact LKR `numeric(12,2)`. The server snapshots the displayed pre-discount/tax base rate at confirmation; absent an approved override, simultaneous rooms of one type share that type's rate, while different types may differ. A changed catalogue quote before confirmation must be shown and reconfirmed. Each line's fixed nightly snapshot survives later catalogue changes; pre-check-in edits preserve previous values in revisions and refresh the DRAFT bill. After check-in the line dates/rate stay fixed, including on a room move; approved differences use explicit invoice adjustments, never retroactive repricing. Physical moves are preserved by assignment occupancy instants. See SRS §4.7.4 for the billing policy.
- Line statuses use BOOKED, CHECKED_IN, CHECKED_OUT, CANCELLED and NO_SHOW with independent per-line check-in/checkout/cancellation/no-show. Booking-wide progress is a read-only summary that must show mixed/partial states honestly. Actual occupied room periods belong to assignments, not their `assigned_at`/`unassigned_at` transaction-time fields.
- `enum(4)`, `enum(11)` and `enum(14)` are source-ER annotations, not PostgreSQL lengths or a required count of labels. The target Member 2 value sets, including the amended physical room conditions, are recorded below.

For M2-S02, catalogue names are required, non-blank `varchar(255)` values; `amenity.description` may be null. Neither catalogue name receives an unapproved uniqueness constraint. `capacity` is positive `smallint`; the rate is non-negative and finite. Both PKs are UUIDv7, and the link table has only its two UUID FKs as composite PK. Link FKs use restricted parent deletion; catalogue records with references are deactivated instead of deleted. These constraints preserve Table 40's attributes without introducing new columns.

The room-type and amenity catalogues have no branch FK, so their values are chain-wide. Under the SRS working role matrix, only CHAIN_MANAGER may edit them, including `room_type.base_daily_rate`; BRANCH_MANAGER may edit physical rooms and dated blocks only in the assigned branch. Member 1 and API owners review/test that role matrix under TBD-15 before dependent write APIs.

M2-S28 guards later capacity/type edits: lowering a room type's capacity must not put any current BOOKED/CHECKED_IN assigned line above capacity, and a room with any such line cannot change type at all because the guest reserved that category. Reject conflicting edits under the same booking/catalogue lock contract; historical lines and agreed rate snapshots stay unchanged.

For the room schema, room numbers are required non-blank `varchar(255)` values and unique within a branch. Every room requires a branch and room type, defaults to active/READY, and has no `booking_id` column. A room block requires a non-blank reason, creator and half-open `[start_date,end_date)` interval with `end_date > start_date`. Dated blocks represent limited outages; physical OUT_OF_SERVICE represents extended outages. New/edited blocks conflict with current overlapping BOOKED/CHECKED_IN assignments, while room/branch/type deactivation or room OUT_OF_SERVICE conflicts with any affected current BOOKED/CHECKED_IN assignment; reassign/cancel before retrying, never delete history. M2-S04 creates this structure directly and M2-S06 enforces assignment/block/active-parent integrity.

Branch deactivation is stricter than an ordinary room move: same-booking cross-branch moves are prohibited, so all affected assignments must close through valid cancellation or completed stays before deactivation.

M2-S05 creates UUIDv7 assignments directly with line/room FKs, ordered `assigned_at`/`unassigned_at` decision instants, actual `occupied_from`/`occupied_to` instants and a partial unique index allowing one open assignment per line. There is no booking-level assignment FK or one-open-per-booking constraint. There is deliberately no simple open-row uniqueness on `room_id`, because different future lines may use a room on non-overlapping dates; M2-S06 enforces same-room interval conflicts and checked-in occupancy. `assigned_at` records when the assignment decision was made, not the hotel-night period or actual occupancy.

## Shared transition and write contract

| Operation | Required atomic writes and checks | Owning member / supplied interface |
|---|---|---|
| Create booking | Validate guest, same branch and every selected line's room, room/branch/type active states, dates, capacity, blocks, physical condition and overlap. Recheck Member 1's latest published chain-wide policy effective on the Asia/Colombo confirmation date, ordered by effective date/publication time/ID so a same-date correction supersedes only for new confirmations; re-quote if it or catalogue rates changed. Insert one header, all BOOKED lines with server-confirmed base-rate snapshots, one open assignment and initial history per line, plus Member 4's single DRAFT invoice linked to that immutable policy, atomically. No applicable policy or any failed line rolls all back. | Member 2 owns creation, line/assignment schema and overlap guard; Member 4 supplies the invoice-create/policy-FK contract. Member 1 supplies staff/online identity, branch scope, `guest_account` ownership and typed policy versions. |
| Modify booking | Revalidate affected line's dates, capacity, branch, blocks and overlap; preserve previous dates/rate/count in revision history. A physical room move closes the old assignment and opens a new one without deleting history. A checked-in move ends/starts actual occupancy segments; past charged nights cannot be overwritten. | Member 2 owns line modification/assignment writes; Member 3 supplies any physical-condition transition/history. Members 2/3 review in-stay policy and lock order. |
| Check in | Normal selected-line BOOKED → CHECKED_IN; verify physical READY and open assignment, start actual occupancy and write line history/audit atomically. Other lines may stay BOOKED; no room-condition history if READY is unchanged. | Member 3 owns check-in. Member 2 supplies line-assignment lookup/guards. Member 1 supplies actor/auth/audit. |
| Check out | Normal selected-line CHECKED_IN → CHECKED_OUT only with consolidated zero balance; end actual occupancy, close its assignment, set that room CLEANING and write line/physical-condition histories/audit atomically. Other lines retain state. | Member 4 owns checkout/balance gate. Member 2 supplies assignment closure/guards. Member 3 supplies condition/history operation. |
| Cancel | Eligible line BOOKED → CANCELLED under policy; close its assignment and release that inventory while preserving history. Whole-booking cancellation applies to every eligible line atomically. Online guest ownership is checked through header guest. | Member 4 owns cancellation/fees/line status; Member 2 supplies assignment/availability; Member 1 supplies ownership/actor/audit. |
| No-show | Eligible line BOOKED → NO_SHOW after its cutoff; close only that assignment and preserve history. | Member 4 owns no-show/line status; Member 2 supplies assignment/availability; Member 1 supplies actor/audit. |

The operation owner writes exactly one `booking_room_line_status_history` row per line transition through Member 2's interface in the same transaction. There is no booking-level status history. Member 3 owns `room_status_history`, written only for real physical-condition changes. Member 1 owns `audit_log`. The database rejects inconsistent direct line/assignment/status writes, including two CHECKED_IN lines on one room or two overlapping active lines for the same room. Members 2–4 use the implemented lock, consistency and safe-retry contract below. Exceptional correction requires a separately audited policy.

M2-S06 implements that database contract. Assignment and active-line rechecks lock the line, booking, target room, branch and room type; block writes lock the target room; parent updates take their own row lock and recheck current assignments. Multi-line procedures must process line and room UUIDs in deterministic order. SQLSTATE `23514` represents a business-state conflict, `23505` covers duplicate open-line assignment, and a caller that receives deadlock `40P01` or serialization failure `40001` retries the complete transaction with bounded backoff rather than replaying only one statement.
