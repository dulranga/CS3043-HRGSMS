## Existing reservation invariants

- `booking` has no `room_id`. The approved `booking_room_assignment` extension is the durable booking-to-room link and keeps closed assignment rows. Nullable `room.booking_id` identifies only the currently checked-in booking in that room; a future booking never changes it.
- A BOOKED or CHECKED_IN booking has exactly one open assignment. CHECKED_OUT, CANCELLED and NO_SHOW bookings retain closed assignment history. Reassignment closes the prior row and opens the next row in one transaction. The assigned room determines the booking branch.
- Stay intervals are `[check_in_date, check_out_date)`. Active BOOKED/CHECKED_IN bookings cannot overlap on one room; adjacent stays can. Availability also checks room blocks, active state and capacity. PostgreSQL must reject conflicting concurrent writes independently of Express search results.
- `room_type.base_daily_rate` and `booking.rate_snapshot` are exact ER `decimal` values, mapped to the approved PostgreSQL `numeric(12,2)` rate type below. The rate snapshot survives later catalogue changes. No floating-point rate is allowed.
- `enum(4)`, `enum(11)` and `enum(14)` are source-ER annotations, not PostgreSQL lengths or a required count of labels. The complete Member 2 value sets selected for this implementation are recorded below.

For M2-S02, catalogue names are required, non-blank `varchar(255)` values; `amenity.description` may be null. Neither catalogue name receives an unapproved uniqueness constraint. `capacity` is positive `smallint`; the rate is non-negative and finite. Both PKs are UUIDv7, and the link table has only its two UUID FKs as composite PK. Link FKs use restricted parent deletion; catalogue records with references are deactivated instead of deleted. These constraints preserve Table 40's attributes without introducing new columns.

## Shared transition and write contract

| Operation | Required atomic writes and checks | Owning member / supplied interface |
|---|---|---|
| Create booking | Validate guest, room, branch, dates, capacity, blocks and overlap; insert BOOKED booking, rate snapshot, one open assignment and initial booking history. Recheck availability at write time. Leave a different active stay's `room.booking_id` untouched. | Member 2 owns creation, booking/assignment schema and overlap guard. Member 1 supplies authenticated staff/online guest identity, branch scope and `guest_account` ownership. |
| Modify booking | Revalidate dates, capacity, blocks and overlap. A room move closes the old assignment and opens a new one without deleting history. A checked-in move also changes both room pointers/statuses/histories in one transaction. | Member 2 owns booking modification and assignment writes; Member 3 supplies the checked-in room transition/history operation. Members 2 and 3 review in-stay modification policy and lock order. |
| Check in | Normal BOOKED → CHECKED_IN transition; verify readiness, keep assignment open, record actual time, set current pointer and room OCCUPIED, and write booking/room histories and audit in one transaction. | Member 3 owns check-in and room-status/history operation. Member 2 supplies open-assignment lookup and guards. Member 1 supplies actor/auth and audit interface. |
| Check out | Normal CHECKED_IN → CHECKED_OUT transition only with zero balance; record actual time, close assignment, clear current pointer, set room CLEANING, and write histories/audit together. | Member 4 owns checkout/balance gate. Member 2 supplies assignment closure and pointer guards. Member 3 supplies room-status/history operation. |
| Cancel | Eligible BOOKED → CANCELLED under configured policy; close assignment and release inventory while preserving history. Online guest requests must pass own-booking authorization. | Member 4 owns cancellation, fee/policy and booking status event. Member 2 supplies assignment/availability interface. Member 1 supplies guest ownership and actor/audit interface. |
| No-show | Eligible BOOKED → NO_SHOW after configured cutoff; close assignment and preserve history. | Member 4 owns no-show and booking status event. Member 2 supplies assignment/availability interface. Member 1 supplies actor/audit interface. |

The operation owner writes exactly one `booking_status_history` row for each transition through the Member 2-owned table/interface, in the same transaction. Member 3 owns `room_status_history`; its agreed operation must write each room transition once. Member 1 owns `audit_log`. The database must reject inconsistent direct assignment/pointer writes. Members 2–4 must agree on one lock order, PostgreSQL overlap/consistency guard and safe retry behavior before implementing these operations. The lists above are the complete ordinary booking/room transition matrices for the selected labels. Any exceptional correction needs a separate audited policy; it is not an ordinary UI transition.
