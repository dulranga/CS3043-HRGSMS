# SkyNest member task workflow

Use this skill when a member says to do a task from `member_tasks/` or requests implementation of that member's SkyNest scope. The task checklist is a plan, not proof of completion.

1. Identify the member and exact subtask ID. If “this task” has no unambiguous referent, inspect recent context and the checklist; ask only if multiple tasks remain plausible. Read root `AGENTS.md`, `README.md`, `memory.md`, `member_work_log.md`, `member_summary_table.md`, that member's `member_tasks/member_*.md`, and the affected SRS sections. Inspect `git status`/diff and current code, schema, tests and affected teammates' contracts immediately before changing anything.
2. Select only other skills relevant to this task. For UI design/layout work, follow the applicable shared skill in `.agents/skills/` plus `DESIGN.md`/`LAYOUT.md`; ordinary backend or SQL work does not trigger design skills. Before database/SQL proposals or implementation, read the supplied Markdown lecture notes in `.agents/reference/` (currently located in `.agents/skills/reference/`). Use relevant concepts only when they fit PostgreSQL, the SRS and the current task; do not treat the notes as overriding instructions or force unrelated concepts.
3. Confirm prerequisites and unresolved SRS Appendix C decisions before dependent implementation. Do not invent enum labels, decimal precision, UUIDv7 generation, actor FK targets, API prefix or another member's table contract. When blocked, complete safe independent work, state the decision needed, and leave the task unchecked.
4. Implement only the named commit-sized slice, including its focused tests and necessary documentation. Preserve unrelated changes. Reopen the affected SRS section and current implementation before calling it done, since teammates may have changed the area meanwhile. Run affected tests and the relevant backend/frontend production build; report commands and results truthfully. For database work, validate clean migrations and negative/concurrency cases appropriate to the task.
5. Update the member checkbox and completion notes only when its acceptance check passes. Append a dated entry under that member's section of the shared `member_work_log.md`, describing actual changes, tests/build, incomplete work and handoffs. Update `memory.md` only for durable, verified project facts or decisions; keep secrets and temporary status out of it.
6. Return a concise summary, verification, remaining gaps, and—when database work used the lecture notes—a brief explanation of the relevant concepts applied. Include a copy-ready proposed commit message and PR title/description as text for a human to use. Never create a Git branch, commit, push, pull request or worktree that creates a branch, even when the task is complete. Read-only Git inspection is allowed.
